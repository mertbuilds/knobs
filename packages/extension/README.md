# @knobs/extension

A Chrome extension that puts the devknobs panel on any page, the same panel as the npm package, with some of its knobs set for real through the Chrome DevTools Protocol (`chrome.debugger`) in place of devknobs' emulation in the page.

Install it from the Chrome Web Store: <https://chromewebstore.google.com/detail/knobs/cpdmafeojnbdnnhldafobkaajiemcidj>. The build steps below are for development.

What it does, how to install it, what Chrome sets for real and the permissions are in the user docs: <https://knobs.dev/docs/extension>. The full reference is at <https://knobs.dev/llms-full.txt>. This file is for working on it.

## How it fits together

- `src/content.ts` runs in the page's own world (`world: "MAIN"`, at `document_start`, in the top frame and in devknobs' width frame), so `window.devknobs` is there for agents as with the npm package. It mounts devknobs with a native driver that sends the knobs Chrome sets for real (text size, offline, the preferences, a plain viewport, the user agent) on, and with no handle on the page's edge, since the toolbar button opens the panel (the panel's settings can show it again).
- Pages that run devknobs themselves. The content script mounts with `host: true`, and before any page script, so its copy holds the page as the host (`Symbol.for("devknobs.host")` beside devknobs' `devknobs.owner` slot on `window`). A copy the page mounts later finds it and puts up no panel: it hands over its `hotkey`, `grabKey`, `grab`, `open` and `grabColor`, and its `unmount()` leaves the extension's panel. `window.devknobs` stays the extension's. The page's early script, inlined in its `<head>`, finds the page held and patches nothing. A copy that knows no hosts (devknobs 0.3.0 and older) takes the page as a hot update would; the extension's copy then takes it back through that copy's own way out, up to three times per page load, then leaves it to the page with a warning in the console. Prefer, in the panel's settings, can give such a page to its own copy instead, a local build say: `PREFER_KEY` in `chrome.storage.local`, kept for the profile by the service worker. The bridge reads it straight from storage as the page starts and hands it to the page as a `prefer` message, and on each change. It can come in after the page's copy mounted, so the handover works whenever it arrives: a copy that knows it leaves the host a way to take the page (`adopt`'s `take`), and the host, preferring the page, unmounts (its native knobs go back to Chrome's) and calls it; the page's copy then mounts as with no host, its settings showing prefer, and the host does not take the page back (nor from a copy that knows no hosts). The content script marks the top window, so devknobs' frame leaves the page to the page's copy there too. Back to the extension from the page's panel loads the page again. A load after a handover starts the extension's copy with `persist: false` (a flag in the tab's `sessionStorage`, read and cleared as the load starts), so it neither reads nor overwrites the stored knobs the page's copy shares. Where the page unmounts its copy after a handover, the toolbar button mounts the extension's copy again, open. Any script of the page can send the prefer message through the bridge, as it can the knobs, the user agent and the bypass: the worst it does is pick who runs the panel.
- `src/bridge.ts` runs in the extension's world in the top frame and carries them between the page and the service worker, as json on `document` events (the page world cannot reach `chrome.runtime`).
- `src/ua.ts` maps a user agent to the request headers the rules set and to the debugger's override.
- `src/background.ts` keeps each tab's knobs, maps them to commands (`src/knobs.ts`) and attaches or detaches the debugger. On each page load the bridge asks for the tab's knobs, and those win over the page's stored ones, so a page on another origin shows what the tab has. The toolbar button opens or closes the panel in the tab. Closing Chrome's debugging bar switches every tab to in-page mode (see [what Chrome sets for real](https://knobs.dev/docs/extension#what-chrome-sets-for-real)); the debugger leaving a tab for another reason, such as the tab closing, puts the panel's knobs back to their defaults.
- The panel keeps the user's own look. The emulated scheme and motion reach every media query in the tab, the panel's too, so `src/offscreen.ts`, an offscreen document outside every tab, reads the real ones. The service worker hands them out with each page load's knobs and sends each change to every tab, and the bridge passes them to devknobs' `setSystemMedia`.
- Framing. The width knob, or a docked panel, loads the tab's own page in a frame, which `X-Frame-Options` or a `frame-ancestors` policy refuses. Only while devknobs' frame is open, one session rule for the tab (`declarativeNetRequest`, its id the tab id) has frame loads in that tab, to and from the page's host, lose `X-Frame-Options` and `Content-Security-Policy`. The page says so as the frame opens, and the frame's first load waits for the rule (devknobs' `native.framed` holds it), so a new tab with knobs that frame it loads the first time. The rule goes as the frame closes, as the tab loads another page (`webNavigation.onBeforeNavigate`) and with the tab.
- A service worker's frame. Where the page's service worker answers the frame's load, the load the rule sees is the worker's own `fetch`, which belongs to no tab, so the rule above misses it. While a tab has devknobs' frame open on a host (the page tells the service worker as the frame opens and goes), one more session rule takes `X-Frame-Options` and `Content-Security-Policy` off what that host's service worker fetches from it: no tab (`tabIds: [-1]`), the host as request and initiator, type `xmlhttprequest` (the type a worker's `fetch` has; `sub_frame` and `other` do not match it). One rule per host, its id from the host's name, gone once no tab has a frame open on the host, a tab closing or loading another page included. The cost: meanwhile, every answer that host's service worker fetches from the network loses those two headers, not only the frame's page. The frame can start loading before the rule is set, so the first refusal on a page with a service worker loads the frame again once, at once, after the rule is in.
- Why a frame was refused. While the debugger is on a tab, the service worker keeps the last few document loads of the tab's frames under the top one (`src/refusal.ts`): the address asked for and where it ended (another host, or Chrome's error page), each redirect, the status, the headers that bear on framing (`X-Frame-Options`, the `frame-ancestors` part of the CSP, `Cross-Origin-*`, `Location`), `Sec-Fetch-Dest` and `Sec-Fetch-Site` as sent, whether a service worker answered and from where, how the load failed (`blockedReason`, the CORS error), and Chrome's own issues (`Audits`) and console lines (`Log`) about it. When devknobs shows its refusal notice, the panel asks for the frame's latest load and says why under the notice in a line, such as `x.com/i/flow/login answered 200 with X-Frame-Options: DENY (from a service worker)` or `redirected to another site: accounts.google.com`, with a "copy details" button for the whole record as json. A service worker's scope comes from the page's own registrations, since the protocol does not give it to an extension. With no knob keeping the debugger on, as for a mocked phone, the line says it was not watching, and "find out why" puts it on, loads the frame again and takes it off once it has the answer. In-page, the line says to turn real browser settings on.
- Past the service worker. A service worker that answers the frame from its own cache sends the refused page itself, which no rule reaches. On a page with a service worker, the notice then offers "load without the service worker (shows Chrome's bar)": the debugger goes on the tab, `Network.setBypassServiceWorker` has the tab's loads, the frame's and the page's own, go to the network, and the frame loads again. It stays so while the frame is open, and through a load of the tab's page on the same host, such as a page that reloads itself once the frame's copy updates its service worker: the page's stored knobs open the frame again, and the bypass waits 15 seconds for it. Once the frame goes, service workers answer again and the debugger leaves, unless a knob keeps it.
- Leaving the frame. A link, form or script in the frame that goes to another origin (a sign-in provider, say, which refuses frames anyway) takes the whole tab there, as it would with no frame; the knobs wait on the page's origin for the way back. A server's redirect to another host still gets devknobs' notice, whose button closes the frame. With the panel closed and no handle, the toolbar button opens it on any page, a framed one too.

## Build and load

```sh
pnpm --filter @vinena/knobs build
pnpm --filter @knobs/extension build
```

The content script bundles devknobs' built package, and `dist/` gets its device images. Then in Chrome: `chrome://extensions`, turn on Developer mode, Load unpacked, pick `packages/extension/dist`.

A local build sets the manifest's `version_name`, and the panel footer, to `<version> · local <label> (<short sha>[+dirty])`: the label is `KNOBS_BUILD_LABEL`, else the branch, else the worktree folder. `CI=true` and `package` builds keep the plain version.

## Store

`pnpm --filter @knobs/extension package` builds `dist/` and zips it to `devknobs-<version>.zip` here (gitignored), the file the Chrome Web Store takes. The version is the manifest's, the devknobs release it bundles. `store/listing.md` holds what the store's dashboard asks for (text, permission justifications, privacy answers), and `store/` the screenshots and the promo tile. The icons are `static/icon-*.png`, from the logo master (see `AGENTS.md`, "Logo"); the 128 is the logo at 96px in 16px of clear space.

## Checks

- `pnpm --filter @knobs/extension test`: the knob to CDP command mapping (`src/knobs.ts`), the headers and override per ua preset (`src/ua.ts`), what a detach tells the tab (`src/messages.ts`) and the record of a frame's load and the line it gives (`src/refusal.ts`), with `bun test`.
- `pnpm --filter @knobs/extension smoke`: loads `dist/` into Playwright's Chromium, drives the panel through `window.devknobs` on a local page and checks what the page sees, in the width knob's frame too, then resets and checks the debugger is off. A page whose policy allows no inline style, and one with `style-src 'self'; style-src-attr 'none'`, gets the panel styled as on any page. Then a page themed from `matchMedia` change events and `light-dark()` flips with the scheme knob, docked too, while the panel keeps the system's look; a page that sends `X-Frame-Options: DENY` and `frame-ancestors 'none'` loads in the frame, in a new tab opened straight to it too, and the framing rule is in only while devknobs' frame is open, its own tab's and host's: with none open, a page's own frame keeps `X-Frame-Options` and its CSP sandbox. The panel shows no handle while closed, where the npm build does. In a window of its own, a plain size and a phone with nothing drawn are the tab's own viewport (its width, ratio and touch screen, no frame, no reload), a mock or a browser drawn around the phone brings the frame back with the override cleared, and reset detaches. In-page mode in a window of its own: the switch off detaches the debugger and the page emulates text size (inline on `<html>`) and frames a plain phone, every knob kept; on again, the debugger is back and the inline size gone; closing Chrome's bar, run through the service worker's handler since a test cannot click the bar, turns it off for every tab with the knobs kept. A link in a frame to another origin moves the tab there. A page whose app takes devknobs' nodes out of `<body>` as it starts, or puts a new `<body>` in, keeps its frame and panel. Why a frame was refused, in a profile of its own: a page that refuses frames, with the framing rule taken off, shows that the debugger was not watching, and "find out why" names its `frame-ancestors` and copies a record with the status, headers and `Sec-Fetch-*`, then the debugger leaves; a frame redirected to another host names that host; a service worker's `X-Frame-Options` answer says it came from one, with its scope; in-page, it says to turn real browser settings on. It shoots that notice to `smoke-out/refusal-cause.png`. Service workers, in a profile of their own: a page whose worker fetches it from a server that refuses frames loads in the frame with no notice, real and in-page, with the worker rule on its host while the frame is open, gone once the frame closes and once the tab closes; a worker that answers from its cache says so under the notice, and its button loads the page past the worker, with a knob on and with none, then closing the frame turns the bypass off and the debugger leaves. The same with a mocked phone on pages whose app clears `<body>` as it starts, puts a new one in, or reloads the tab once the frame's copy loads past the worker: the frame ends up showing the page with the bypass on and the debugger attached, and both go with the frame. What servers see, in a profile of its own: a page with a service worker, under the ua knob, sends the preset's user agent and client hints (none for iPhone Safari; `?1` and `"Android"` for Android Chrome) on its load, a fetch, an image and a fetch its service worker makes, with no debugger, in real mode with it (where the page and a worker of its read the same) and in-page; another tab keeps Chrome's own; an iPhone 18 Pro's frame loads as the iPhone, and again as Android Chrome after a change; system puts Chrome's own back and drops the rules. A page that mounts devknobs' module build itself, with a hotkey and grab's color of its own, keeps one panel, the extension's, with the page's hotkey and color, and the page's `unmount()` leaves it; a copy that claims the page as 0.3.0 does is taken over and its panel goes. Prefer, in a profile of its own, on a page that mounts a local build of devknobs (the module build served with a `-local.123` version): extension keeps one panel, the extension's, its footer `extension <version>`; picking page in its settings hands the page over at once, one panel, the page's, its footer `page <version>-local.123`, with no take-back, through a load again too; a page with no copy of its own keeps the extension's; the page's knobs set in its panel last a load again; the page unmounting its copy and the toolbar button bring the extension's panel back, open; picking extension in the page's panel loads the page again with the extension's. It shoots both settings to `smoke-out/prefer-extension.png` and `prefer-page.png`. The npm build on a page with `style-src 'self'; style-src-attr 'none'` draws the same pixels as on one with no policy, with the panel open, a knob's editor open, grab's overlay, a refused frame's notice and a phone's mock. It also shoots the open panel with the extension and with the npm build, and the settings with the switch, into `smoke-out/`. Build first. `bun scripts/build.ts <dir>` and `node scripts/smoke.ts <dir>` build and check another directory than `dist/`, so a work in progress never lands in the one Chrome loads. Needs Playwright's Chromium (`pnpm exec playwright install chromium`); branded Chrome ignores `--load-extension`. CI runs it on every PR, on local pages only.
